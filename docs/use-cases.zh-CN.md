# 应用场景指南：每个菜谱是做什么用的

[English](use-cases.md) · **简体中文**

本指南针对每个菜谱回答三个问题：

1. **它做什么？** 用大白话讲，不用术语。
2. **什么时候用它？** 它解决哪一类问题。
3. **在实际工作中出现在哪里？** 来自不同岗位的具体场景。

本指南 **不** 讲配置步骤和单个节点，那是每个菜谱自己的 README 的内容。

## 先搞清楚：n8n 到底是干什么的？

n8n 把各种应用和数据 **连接起来，不需要你在中间手动搬运**。只要你发现自己在手动做下面这些事，基本都能交给工作流：

- **复制** 信息到另一个地方（邮件 → 表格、表单 → CRM）
- **定期检查** 某样东西（网站挂了吗？出新版本了吗？价格变了吗？）
- **对事件做出反应**（有人提交了表单、收到了付款、来了一张工单）
- **转换** 数据（清洗杂乱的名单、合并两份导出数据、从 PDF 中提取字段）
- **通知** 相关的人（每日汇总、告警、审批请求）

每个工作流都是同一个形状：

```
   当某件事发生时   →   执行这些步骤   →   把结果发到某处
   （触发器）           （节点）            （邮件、聊天、表格、API 响应……）
```

这 20 个菜谱就是这个形状的 20 种变体。每个都教你一个会反复用到的模式。

## 第一部分 · 基础

### 01 · Hello Webhook API

**它做什么：** 给 n8n 一个专属的网址。有数据发到这个网址时，n8n 处理它并返回结果。

**打个比方：** 一个能自动回信的信箱。来一封信，n8n 读完，立刻寄回回信。

**适用情况：** 另一个工具需要在事情发生的那一刻把信息 *推送* 给你，而不是你自己去查。

**实际场景**
- **网店：** 每来一个新订单，Shopify、WooCommerce 或有赞就调用你的 Webhook。n8n 随后更新库存、通知仓库、感谢顾客。
- **市场：** 落地页工具（Webflow、Typeform、金数据）把每个报名发给 n8n，n8n 再把它加到邮件列表里。
- **开发：** 一个迷你内部 API（“告诉我今天谁值班”），不用写代码、不用部署服务器。
- **支付：** Stripe 告诉你“付款成功”，n8n 就开通客户的账号。

**实际使用时要改的：** 收到请求和返回结果之间做什么。“请求进来、响应出去”的框架保持不变。

**是这些菜谱的基础：** 09、13、16、17、19 都以 Webhook 开头。

### 02 · 每日天气播报

**它做什么：** 每天早上从公开服务获取数据，整理成一条简短友好的消息。

**打个比方：** 一个每天同一时间帮你查好东西、再把结论告诉你的助理。

**适用情况：** 你每天固定时间都要查同样的信息，希望它自动送到面前。

**实际场景**
- **销售：** 每周一 9:00，把上周 CRM 里的业绩数字发到团队群。
- **运营 / 外勤：** 户外作业（工地、配送、活动）在可能下雨时收到天气预警。
- **财务：** 每天一条汇率或股价提醒。
- **个人：** 把日程、待办和天气合成一条早间消息。

**实际使用时要改的：** 调用的 API（任何提供 REST API 的服务都行）以及消息发到哪里（Slack、Teams、飞书、钉钉、企业微信、邮件）。

**关键模式：** *定时 → 获取 → 整理 → 发送。* 这可能是世界上最常见的工作流形状。

---

### 03 · RSS 新闻摘要邮件

**它做什么：** 每个工作日读取一个新闻源，只保留当天的新闻，汇总成 **一封** 整洁的摘要邮件。

**打个比方：** 一位私人编辑，替你读完新闻，再发你一页纸的摘要。

**适用情况：** 信息是一条一条零散到来的，但你只想要 **一份** 汇总，而不是被一堆通知淹没。

**实际场景**
- **市场 / 公关：** 每天汇总提到你的品牌或竞品的新闻（很多新闻站和 Google 快讯都提供 RSS）。
- **产品团队：** 每周一封邮件，汇总你关注的行业博客的新文章。
- **科研：** 来自 arXiv 或期刊 RSS 的本领域新论文。
- **客服：** 每晚列出论坛里还没人回复的新问题。

**实际使用时要改的：** 订阅源地址、筛选条件（关键词、日期）和收件人。

**关键模式：** *多条数据 → 筛选 → 合并成一条 → 只发一次。* 任何叫“摘要”“日报”“周报”的东西都用这个模式。

### 04 · 联系表单 → Google Sheets

**它做什么：** 发布一个网页表单（由 n8n 托管，不需要网站），清理每次提交的内容，并作为一行追加到 Google Sheets。紧急请求走单独的分支。

**打个比方：** 一位前台：记下留言，工工整整写进登记簿，遇到急事马上跑来告诉你。

**适用情况：** 需要别人提交结构化的信息，并希望它自动整齐地存放到某处。

**实际场景**
- **小企业：** 联系表单或报价申请 → 表格 → 紧急的立即提醒。
- **人事：** 求职申请、请假申请、设备领用申请。
- **活动：** 报名信息（包括饮食需求）直接进入参会名单。
- **IT：** 内部“问题上报”表单，紧急问题转给值班人员。

**实际使用时要改的：** 表单字段、存储位置（Airtable、Notion、飞书多维表格、HubSpot、菜谱 19 的 Data Table），以及“紧急”时触发什么（群消息、短信）。

**关键模式：** *收集 → 清洗 → 存储 → 分流。*

### 05 · API 数据 → CSV 导出

**它做什么：** 从在线服务下载 **全部** 记录，哪怕服务是一页一页地返回。然后只保留你关心的记录，保存成表格文件。

**打个比方：** 有人帮你把整本商品目录一页页翻完，勾出符合条件的商品，再录入 Excel。

**适用情况：** 需要把数据从某个工具里 *导出来*，但它没有好用的导出按钮，或者每次导出都要筛选。

**实际场景**
- **电商：** 每晚导出库存不足或评分差的商品。
- **财务：** 每月从账单工具导出所有发票交给会计。
- **市场：** 本季度新增的全部订阅用户。
- **数据分析：** 把 SaaS 的 API 数据拉成 CSV，交给 Excel、Power BI、Looker Studio 或帆软等 BI 工具。

**实际使用时要改的：** API 地址、分页设置（README 里有常见分页方式的速查表），以及文件发到哪里（Google Drive、邮件、S3、阿里云 OSS）。

**关键模式：** *取完所有页 → 拆成记录 → 筛选 → 整形 → 导出。*

---

### 06 · 网站可用性监控

**它做什么：** 每 5 分钟访问一遍网站列表。只要有网站挂了，就发 **一条** 告警，列出所有出问题的网站。

**打个比方：** 一位夜班保安，挨个检查每扇门，只有出问题时才叫醒你。

**适用情况：** 你需要在客户发现之前，尽快知道有东西停止工作了。

**实际场景**
- **自由职业者 / 外包团队：** 用一个工作流监控所有客户的网站。
- **开发：** 检查应用的健康检查接口和 API 是否有响应。
- **电商：** 确认结算页能打开（并且页面里包含“结算”字样）。
- **IT：** 监控内部系统（内网、VPN 门户）是否宕机。

**实际使用时要改的：** 网址列表（或从表格中读取）、检查间隔和告警渠道。用菜谱 07 的“记忆”技巧，可以避免同一次故障反复告警。

**关键模式：** *一组对象 → 逐个检查 → 收集失败项 → 只告警一次。* 同样的模式也适用于 SSL 证书到期、域名续费、磁盘空间检查。

### 07 · GitHub 新版本监控

**它做什么：** 每小时检查几个软件项目有没有发布新版本。只在 **真正有新内容** 时才通知你，同一条提醒绝不发两次。

**打个比方：** 一个帮你盯着橱窗的朋友，只有橱窗陈列变了才给你打电话。

**适用情况：** 你在盯着某样东西的变化，而重复的“没有新内容”或重复提醒会让人烦。

**实际场景**
- **开发 / IT：** 及时知道你依赖的工具发布了更新或安全补丁。
- **采购：** 某个商品页的价格或库存变了（可以结合菜谱 20）。
- **招聘：** 你关注的招聘页出现了新职位。
- **合规：** 某条法规或政策页面更新了。

**实际使用时要改的：** 监控的对象，以及如何判断“是同一个东西”（版本号、ID、URL）。

**关键模式：** *检查 → 与记忆对比 → 只处理新内容 → 记下来。* 这是所有“有变化时通知我”类自动化的核心。

---

### 08 · 合并两个 API 的数据

**它做什么：** 从一个数据源拿到人员名单，从另一个数据源拿到他们的活动记录，按 ID 对上，生成一份合并报表。

**打个比方：** 把两张打印出来的名单并排放好，把对应的数字抄过去，只不过一瞬间完成而且不会出错。

**适用情况：** 完整的信息分散在两个互不相通的系统里。

**实际场景**
- **销售：** CRM 联系人 + 账单系统 → 哪些客户有未付发票？
- **人事：** 员工名单 + 工单系统 → 谁手上的未结工单太多？
- **电商：** 订单 + 物流状态 → 哪些订单延误了？
- **市场：** 订阅用户 + 购买记录 → 哪些订阅用户从没买过东西？

**实际使用时要改的：** 两个数据源、用来匹配的字段（常用邮箱），以及保留全部行还是只保留匹配上的行。

**关键模式：** *两个数据源 →（可选：先汇总其中一个）→ 按共同字段合并 → 出报表。* 注意 README 中讲到的“文本和数字类型不一致”的坑。

### 09 · AI 客服工单分拣

**它做什么：** 收到一条客服消息时，AI 读完它，填好一张小表：类别、优先级、情绪和一句话摘要。然后工单自动转给对应团队。

**打个比方：** 一位手脚很快的助理，读完每封来信，贴上一张便签，放进对应的收件篮。

**适用情况：** 你收到的是自由文本，目前需要有人逐条阅读，只是为了决定它该交给谁。

**实际场景**
- **客服：** 把工单分给账务、技术或销售；愤怒或紧急的工单优先升级。
- **销售：** 阅读询盘，提取公司名、预算和时间线，写入 CRM。
- **人事：** 按岗位给简历分类，提取工作年限。
- **运营：** 把格式混乱的订单邮件变成结构化订单。

**实际使用时要改的：** 提示词中的类别和规则、模型（可换成 DeepSeek、通义千问等），以及每个分支发往哪里（Zendesk、Jira、飞书、钉钉……）。先记录一段时间 AI 的判断结果，核对准确率。

**关键模式：** *非结构化文本 → AI 提取结构化字段 → 常规路由。* AI 只负责“读懂”这一步，后面都是普通的 n8n。

### 10 · 错误处理与告警

**它做什么：** 展示自动化的几道安全网：服务偶尔出错时自动重试；真的失败时走备用方案；遇到意外故障时通知人。

**打个比方：** 给你所有其他工作流装上烟雾报警器和灭火器。

**适用情况：** 只要工作流重要，也就是 **任何你依赖的工作流**。悄无声息地失败的自动化，比没有自动化更糟。

**实际场景**
- **所有团队：** 一个共享的“错误告警”工作流，任何工作流失败时都发到 #自动化告警 频道。
- **系统集成：** 合作方 API 不稳定时，先重试 3 次再放弃。
- **报表：** 实时数据源挂了，就发送昨天的缓存数据并标注“（缓存）”，而不是什么都不发。
- **数据质量：** 订单金额为负数时，主动停止并给出清晰的错误信息。

**实际使用时要改的：** 告警渠道，并把错误工作流挂到每个生产工作流上（*Settings → Error Workflow*）。

**关键模式：** *重试 → 备用方案 → 明确失败 → 告警。* 在你依赖任何工作流之前，先把这些加上。

## 第二部分 · 进阶

### 11 · 限速批量地理编码

**它做什么：** 为一串城市查询详细信息（经纬度、国家、人口）。**每次 3 个，中间暂停一下**，最后把所有结果汇总成一个文件。

**打个比方：** 搬箱子上楼时一次搬几个，而不是一口气全搬，最后在楼上整整齐齐码好。

**适用情况：** 你要向一个限制调用速度的服务发送大量请求（大多数服务都有限制）。

**实际场景**
- **销售 / 市场：** 用企业信息服务（如 Clearbit、Apollo、企查查等的 API）补全 2000 条线索。
- **物流：** 批量把配送地址转成坐标。
- **AI：** 用大模型总结 500 份文档，又不超过每分钟的调用上限。
- **数据迁移：** 把几千条记录导入一个每秒只接受 10 条的新系统。

**实际使用时要改的：** 列表来源、批大小和暂停时长（参照 API 文档中的限制），以及 API 本身。

**关键模式：** *列表 → 分批 → 调用 → 暂停 → 循环 → 汇总。*

### 12 · 可复用的通知子工作流

**它做什么：** 把“发送一条格式统一的通知”放进一个 **独立的小工作流**，任何其他工作流都能调用它，就像工具箱里的一件公共工具。

**打个比方：** 公司的收发室。每个部门把信交过去，格式和投递都按同一个标准处理。

**适用情况：** 你发现自己在好几个工作流里搭了同样的步骤。

**实际场景**
- **所有团队：** 一个统一的“通知”工作流。把 Slack 换成飞书只改一处，30 个工作流全部跟着变。
- **销售：** 一个共享的“在 CRM 中查找或创建客户”步骤，供表单、邮件和导入流程共用。
- **数据：** 一个共享的“把事件写入审计表”步骤。
- **AI：** 子工作流可以变成 AI 智能体能调用的 **工具**（见菜谱 15）。

**实际使用时要改的：** 子工作流做什么、需要哪些输入。调用的方式不变。

**关键模式：** *小而可复用的积木。* 这是 n8n 规模变大后仍然好维护的关键。

### 13 · 带 HMAC 签名的安全 Webhook

**它做什么：** 只有带着有效签名的 Webhook 数据才会被接受，签名能证明数据来自预期的发送方，并且在途中没被篡改。其他请求一律返回“401 Unauthorized”。

**打个比方：** 一个盖着火漆印的信封，只有你和寄信人知道怎么盖这个印。封口破了或印章是假的，信就会被退回。

**适用情况：** Webhook 会触发重要的操作：付款、账号变更、订单。

**实际场景**
- **支付：** 确认“付款成功”的通知真的来自 Stripe、Paddle 等支付平台。
- **电商：** 发货前先验证 Shopify 订单 Webhook 的签名。
- **开发：** 部署代码前先验证 GitHub Webhook。
- **内部系统：** 让你自己的应用用共享密钥安全地调用 n8n。飞书、钉钉机器人的“加签”也是同样的原理。

**实际使用时要改的：** 密钥，以及你的服务商使用的请求头名称和格式（README 中有对照表）。

**关键模式：** *先验证，再信任。* 任何对外公开的 Webhook，都可以把它和菜谱 01 的模式结合起来用。

---

### 14 · 联系人清单清洗与去重

**它做什么：** 拿到一份杂乱的表格后：
- 统一修正姓名、邮箱、电话和日期
- 剔除有问题的行，并写明每一行的原因
- 去掉重复项
- 输出一个干净的文件

**打个比方：** 一位细心的实习生，几秒钟就把表格整理干净，还会告诉你扔掉了哪些行、为什么。

**适用情况：** 数据来自人工填写或系统导出，在进入重要系统之前需要先统一规范。

**实际场景**
- **市场：** 把活动报名名单导入邮件工具前先清洗。
- **销售：** 合并多个展会的线索名单且不重复。
- **人事：** 迁移到新的人事系统前，统一员工数据格式。
- **财务：** 统一银行导出文件中的日期和数字格式。

**实际使用时要改的：** 输入来源（Google Drive、邮件附件、上传表单）、列名和校验规则。

**关键模式：** *读文件 → 规范化 → 校验（附原因）→ 去重 → 导出。*

---

### 15 · 带工具和记忆的 AI 智能体

**它做什么：** 一个聊天助手，**自己决定** 什么时候去查资料。在这里，它会查询实时汇率、使用计算器，还记得你在对话里之前说过的话。

**打个比方：** 一位可以对话的助理，手边有电话（用来查资料）、计算器和记事本。

**适用情况：** 用户的问题千变万化，回答时需要查资料或执行操作，而不只是凭已有知识回答。

**实际场景**
- **客户服务：** 网站上的聊天机器人，能查询订单状态、配送时间和常见问题。
- **内部服务台：** “我还剩几天年假？”（智能体查询人事系统）
- **销售：** “上个月我们给 ACME 报的价是多少？”（智能体搜索 CRM）
- **运营：** “给 3 楼坏掉的打印机建一张工单”（智能体调用工单系统）

**实际使用时要改的：** 工具（任何 API、子工作流或数据库都能变成工具）、系统消息（规则和语气），以及记忆的存储方式（用数据库，重启后对话也不会丢失）。

**关键模式：** *AI + 工具 + 记忆 = 智能体。* 先从 2–3 个描述清晰的工具开始。如果每个请求都走同样固定的步骤，菜谱 09 的做法更合适。

---

### 16 · 人工审批流程

**它做什么：** 小额报销自动通过。大额报销会给经理发送 *同意* / *拒绝* 链接，工作流随即 **暂停**，直到有人点击其中一个，再从暂停的地方继续。

**打个比方：** 把文件放进某人的待批篮，等他签完字后继续办手续，而且不需要任何人记着这件事。

**适用情况：** 活交给自动化来干，但决定必须由人来做（或确认）。

**实际场景**
- **财务：** 超过额度的报销、采购单或退款审批。
- **市场：** AI 起草的社交媒体文案，审批通过后才发布。
- **人事：** 经理批准请假后，自动更新日历和人事系统。
- **IT：** 经理批准权限申请后，自动开通账号。

**实际使用时要改的：** 审批金额门槛、通知审批人的方式（邮件、Slack、飞书、Teams），以及批准之后要做什么。n8n 的 Slack、Gmail、Teams 节点也自带现成的 *Send and Wait for Response* 操作。

**关键模式：** *自动执行 → 暂停等人 → 继续执行。* 这样就能安全地自动化那些你还不放心完全交出去的决定。

---

### 17 · 用 Webhook 提供 HTML 看板

**它做什么：** 打开一个链接，就会看到一个实时网页（这里是带小趋势图的汇率看板），由 n8n 当场生成。不需要网站，也不需要服务器托管。

**打个比方：** 一块公告板，每次有人看它时都会自动换上最新的数字。

**适用情况：** 需要让人 *看到* 数据，而表格或聊天消息都不是合适的形式。

**实际场景**
- **管理层：** 简单的 KPI 页面（今日销售额、未结工单、新注册数）。
- **运维：** 显示菜谱 06 监控结果的状态页。
- **客户：** 每个客户一个私密的项目进度页（加密码保护）。
- **活动：** 实时报名人数计数器。

**实际使用时要改的：** 数据来源和页面布局。在 Webhook 上开启 *Basic Auth*，页面就是私密的。

**关键模式：** *收到请求 → 获取数据 → 生成 HTML → 返回页面。* 再加一个提交到另一个 Webhook 的表单，就成了一个迷你网页应用。

### 18 · PDF 发票解析

**它做什么：** 读取 PDF 发票，提取发票号、日期、明细行和金额，变成结构化数据，然后核对金额是否对得上。

**打个比方：** 一位会计，读完每张发票、录入系统，并把算不对账的发票挑出来。

**适用情况：** 信息以 PDF 形式到来，但你需要把它变成能保存、汇总或继续处理的数据。

**实际场景**
- **财务：** 邮箱里的供应商发票 → 记账表格或 Xero、QuickBooks、金蝶、用友等财务软件。
- **物流：** 从送货单中提取运单号。
- **法务 / 人事：** 从标准合同或表单中提取日期和姓名。
- **销售：** 读取客户的采购订单并创建订单。

**实际使用时要改的：** PDF 的来源（邮件触发、Google Drive 文件夹、上传表单）和提取规则。版式差异很大时，改用 AI（菜谱 09 的模式）。

**关键模式：** *文件 → 文本 → 结构化字段 → 校验 → 入账或人工复核。* 注意那个“复核”分支：看起来不对劲的数据仍由人来检查。

---

### 19 · 用 Data Tables 做迷你 CRM

**它做什么：** 把联系人存进 n8n **内置** 的数据库，并提供一个小小的网页 API 来新增、更新和查询联系人。更新时只修改你传入的字段。

**打个比方：** 一个放在 n8n 里面的文件柜，前台负责按要求归档、更新和取出卡片。

**适用情况：** 你的工作流需要记住一些结构化信息，而专门去配 Google Sheets、Airtable 或真正的数据库又太重。

**实际场景**
- **小企业：** 由联系表单（菜谱 04）自动录入的轻量线索名单。
- **自动化状态：** 记住哪些客户已经收到过欢迎邮件。
- **查询表：** 一张“产品编码 → 负责团队”的对照表，工作流在分派前先查一下。
- **AI 智能体：** 智能体可以查询的记忆表或资料表（菜谱 15）。

**实际使用时要改的：** 数据表和列、校验规则，并给 Webhook 加上身份验证。如果很多人需要手工编辑这些数据，共享表格或正式的 CRM 更合适（见 README 中的对比表）。

**关键模式：** *存储 → upsert（有则更新、无则新增）→ 查询。* 这是你在 n8n 里的第一个数据库。

### 20 · 用 HTML 节点抓取网页

**它做什么：** （慢慢地、有礼貌地）访问一个商品目录的好几页，挑出书名、价格和评分，把高分且有货的商品保存成表格。

**打个比方：** 有人替你浏览网站，把感兴趣的内容抄进一张表。

**适用情况：** 你需要的信息在某个网站上，但它 **没有 API 也没有导出功能**，并且你被允许采集。

**实际场景**
- **电商：** 跟踪竞品在公开商品页上的价格（结合菜谱 07，价格变化时提醒）。
- **房产 / 招聘：** 收集符合条件的新房源或新职位。
- **研究：** 采集政府或统计网站上公开的数据表。
- **市场：** 检查自家网站的页面有没有缺标题或价格显示错误。

**实际使用时要改的：** 网址和 CSS 选择器（README 教你怎么找）。一定先查看网站的使用条款和 `robots.txt`，有官方 API 或 RSS 时优先使用。在中国境内采集数据还要遵守《个人信息保护法》等相关法规。

**关键模式：** *页面列表 → 慢速获取 → 提取 → 清洗 → 导出。*

## 把菜谱组合起来

真实的自动化通常会组合多个模式。下面是四个完全用本仓库菜谱搭成的真实系统：

### 小企业线索流水线
```
联系表单（04）→ 清洗数据（14）→ AI 阅读留言并给线索打分（09）
→ 存入联系人表（19）→ 紧急线索请老板快速决定（16）
→ 全程由错误工作流保护（10）
```

### IT / 运维监控
```
每 5 分钟检查网站（06）→ 记住哪些已经挂了，避免刷屏（07）
→ 通过共享的通知子工作流发送（12）→ 在网页上显示状态（17）
```

### 应付账款助手
```
供应商邮件发来 PDF → 提取发票字段（18）→ 超过 1000 元需要审批（16）
→ 已批准的发票记入数据表（19）→ 每周发一封到期付款汇总邮件（03 的模式）
```

### 客服助手
```
来自客服系统的签名 Webhook（13）→ AI 分拣（09）
→ 简单问题由能查订单的智能体回答（15）
→ 其余转给对应团队（09）→ 出错时告警（10）
```

## 应该从哪些菜谱开始？

| 如果你是…… | 从这里开始 | 然后 |
|---|---|---|
| **完全没接触过自动化** | 01 → 02 → 04 | 03、06 |
| **经常和表格、数据打交道** | 05 → 14 → 08 | 11、18、20 |
| **对 AI 感兴趣** | 01 → 09 → 15 | 16（AI + 人工审批） |
| **运营网站或应用** | 06 → 13 → 10 | 07、17 |
| **搭建内部工具** | 04 → 19 → 17 | 12、16 |

无论走哪条路线，在日常依赖任何工作流之前，都请先学完 **10（错误处理）**。

## 术语表

| 术语 | 通俗解释 |
|---|---|
| **工作流（Workflow）** | 一个自动化流程：一个触发器加上后续的步骤。 |
| **节点（Node）** | 工作流中的一个步骤（画布上的一个方块）。 |
| **触发器（Trigger）** | 启动工作流的事件：定时、Webhook、表单、新邮件…… |
| **数据项（Item）** | 在工作流中流动的一条记录（一个订单、一行数据、一封邮件）。大多数节点对每个数据项各运行一次。 |
| **表达式（Expression）** | 写在 `{{ }}` 里的小公式，用来读取或计算数据，例如 `{{ $json.email }}`。 |
| **Webhook** | 一个网址，有数据发过来时就启动工作流。 |
| **API** | 程序之间对话的方式。“调用 API”就是向某个服务要数据，或让它做某件事。 |
| **凭证（Credential）** | 保存好的登录信息或 API Key，n8n 用它代表你访问某个服务。 |
| **发布（Publish）** | 打开工作流，让它自动运行（旧版本中叫 *activate* / 激活）。 |
| **执行记录（Execution）** | 工作流的一次运行。可以在 *Executions* 中查看历史运行。 |
| **子工作流（Sub-workflow）** | 被另一个工作流调用的工作流，类似可复用的函数。 |
| **智能体（Agent）** | 能自己决定使用工具（API、计算器、数据库）来完成任务的 AI。 |
